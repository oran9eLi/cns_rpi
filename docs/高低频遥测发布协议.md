# 高低频遥测发布协议

版本：2026-11-06

状态：已实施（树莓派端）

## 1. 目标

F407 主控箱使用两条同构的 MQTT 发布通道。两条通道都从同一个
`TelemetryState` 读取当前最新状态，差别只在发布周期和 JSON 字段范围：

- 快照通道按低频发布完整状态，供服务器维护设备状态和数据库；
- 实时通道按高频发布快变字段，供当前正在查看设备的 Web 页面使用。

发布器不保存历史帧。MQTT 发布失败时丢弃本周期帧，下一周期重新采样最新状态，
不重传、不补发，避免旧数据积压后放大显示延迟。

## 2. MQTT Topic

| 通道 | Topic | 默认周期 | QoS | Retain |
|---|---|---:|---:|---:|
| 快照 | `{namespace}/{device_id}/telemetry/snapshot/v1` | 1000 ms（1 Hz） | 0 | false |
| 实时 | `{namespace}/{device_id}/telemetry/realtime/v1` | 100 ms（10 Hz） | 0 | false |

`device_id` 始终来自 F407 `OPEN_DRONE_ID_BASIC_ID.uas_id`；可选 RTK 的 PX4 Basic ID 仅放在实验元数据中。设备不会双发旧的
`{namespace}/{device_id}/telemetry` Topic。

设备在线状态仍由 retained registration 表达，不能根据遥测是否有 retained 消息判断。

## 3. 配置

```json
{
  "telemetry_publish": {
    "snapshot": {
      "enabled": true,
      "interval_ms": 1000
    },
    "realtime": {
      "enabled": true,
      "interval_ms": 100
    }
  },
  "mqtt": {
    "topics": {
      "telemetry_snapshot": {
        "suffix": "telemetry/snapshot/v1",
        "qos": 0
      },
      "telemetry_realtime": {
        "suffix": "telemetry/realtime/v1",
        "qos": 0
      }
    }
  }
}
```

- 快照周期允许 100～60000 ms；
- 实时本地配置周期允许 50～60000 ms，即上限 20 Hz；远程调频允许 100～60000 ms；
- 两个 Topic 后缀必须非空、互不相同，也不能与其他数据、注册、命令或 ACK Topic 重名；
- 两个通道的 QoS 固定为 0，retain 固定为 false；
- 远程参数名 `telemetry_publish_interval_ms` 为兼容既有命令保持不变，但只更新
  `telemetry_publish.snapshot.interval_ms`。

服务器也可使用 `config/set.parameters.topic_publish_intervals_ms` 分别热改两个数据 Topic 的周期，实验运行中可用，保存成功后无需重启。完整格式与其他数据 Topic 规则见 [Topic 上报周期控制接口](Topic上报周期控制接口.md)。

`deploy.sh` 在重启主程序前幂等迁移旧现场配置，通过暂存候选和配置 helper 原子应用。旧版快照周期保持原值；废弃的 `px4_realtime` 直接丢弃，新实时通道使用启用、100 ms 默认值。已使用 `telemetry_publish` 的通道参数保持不变。旧 `device.mode=auto|cns_box` 和关闭的 `qgc_udp` 会移除，其他设备模式或已启用的桥接明确拒绝。已经是当前结构的配置不会重新格式化或写回。当前源码部署使用普通可写根文件系统；旧只读部署迁移见新设备部署手册。

## 4. JSON 字段边界

### 4.1 快照帧

快照帧继续使用 `schema_version=3`，包含当前已知的完整遥测、5G 链路状态、模块、
告警、日志和 Open Drone ID 数据。未收到的字段省略，不输出 `null` 占位对象。

```json
{
  "schema_version": 3,
  "device_id": "DCDWCNS1S2MEAG1VTA0C",
  "device_type": "cns_box",
  "school_name": "SEU",
  "sent_at": "2026-08-04T02:00:00Z",
  "telemetry": {
    "motor": {},
    "cellular_5g": {}
  },
  "modules": [],
  "alarms": {},
  "logs": {},
  "drone_id": {}
}
```

### 4.2 实时帧

实时帧使用独立的 `schema_version=1`，`sent_at` 保留毫秒，`sequence` 按 MQTT 会话
内每个通道从 0 递增。它包含主控箱已收到的电机与动态字段：

```json
{
  "schema_version": 1,
  "device_id": "DCDWCNS1S2MEAG1VTA0C",
  "sequence": 42,
  "sent_at": "2026-08-04T02:00:00.123Z",
  "telemetry": {
    "heartbeat": {},
    "attitude": {},
    "gps": {},
    "global_position": {},
    "sys_status": {},
    "battery": {},
    "pressure": {},
    "motor": {
      "duty_percent": [10, 20, 30, 40],
      "run_state": true,
      "speed_level": 2,
      "pwm_us": [1500, 1510, 1520, 1530],
      "pwm_time_usec": 123456
    }
  }
}
```

实时帧不携带 `school_name`、`device_type`、`cellular_5g`、`modules`、`alarms`、
`logs` 或 `drone_id`。具体快变字段仍遵循“收到才输出”的规则，不根据未收到的字段构造数据。

BMI088 IMU 已在 Pi 侧接入：快照／实时新增 `telemetry.imu`，完整原始采样对使用独立 `imu/sample/v1`。字段、JSON、200ms 有效期和 STATUS 规则见 [IMU 原始与解析数据接口](IMU原始与解析数据接口.md)，实现与验证边界另见该文档第 7 节。

### 4.3 显式 RTK 第一实验增量

`rtk_base.enabled=true` 时在原 F407 主流程复用以上两个 Topic、周期和 schema；外层 `device_id` 为箱子 F407 身份，快照设备类型仍为 `cns_box`。两类帧均增加 `telemetry.rtk={base,px4,box_identity_verified}`。`base` 与 [RTK 本地/动作状态](RTK基站第一实验操作与接口.md)中的基站状态一致，包括串口、协议版本、新鲜度、Survey-in、RTCM 校验计数与 RAM 配置读回状态；`px4` 包含独立 3DR/PX4 链路的状态、身份元数据和真实遥测；`box_identity_verified` 为布尔值，表示 F407 当前链路身份是否已核验。原 F407 遥测与快照中的 5G 信息保持原来源，不能用 PX4 状态覆盖。

基站状态里的未知字段使用 `null`，并以 `known/stale` 区分缺少与过期证据。基站独立连接、配置 `verified`、Survey-in `completed`、RTCM 有效帧和移动站 RTK Fixed 各自判断，不能互相替代。PX4 实时身份失效只撤销 `rtk.px4` 的实时数据，不关闭箱子 MQTT，本地基站观测继续。已有合法持久化箱子绑定且无身份冲突时，允许缓存身份的 RTK 发布；F407 未实时业务在线时，此新帧不包含其旧普通传感数据，runtime 如实为 cached/offline/unknown，并通过 `box_identity_verified` 明示当前核验状态。没有箱子绑定时仅保留本地 base/PX4，不使用 PX4 注册。未启用 RTK 时保持原发布门禁且不增加该对象。

缓存 RTK 快照的 schema 3 仍保留精确空 `"drone_id":{"basic_id":{}}`：现有服务器 `ParseTelemetry` 要求这两层为对象，缺少容器会拒绝快照。容器内不填 `id_type`、`ua_type` 或任何 F407 实时观测值，也不据此核验身份；schema 1 实时帧仍不含 `drone_id`。此项由 Pi 适配现有接收合同，不改服务器代码。

## 5. 服务端消费边界

2026-11-09 RTK移动站增量：`telemetry.rtk`增加`relay/observation`、`px4.gps_observation/firmware`。低频快照保留完整UBX/RTCM/GPS和实际发送MAVLink样本；高频实时帧省略所有原文及变化历史。不得用高频缺字段覆盖低频原文窗口。独立GPS样本3秒未更新即过期，重复源时间不刷新测量年龄，过期时旧`px4.telemetry.gps`也省略。精确字段及证据边界见 [移动站实验与教学数据接口](RTK移动站实验与教学数据接口.md)。

- 数据库和设备状态维护服务只订阅快照 Topic；
- Web 实时服务只为当前正在查看的 `device_id` 订阅实时 Topic；
- 禁止服务端常驻通配订阅全部实时 Topic 后再按页面筛选；
- Web 侧每台设备最多保留最新一帧，处理不过来时覆盖旧帧；
- 服务端必须先兼容新 Topic，再升级树莓派。设备端不双发旧 Topic。

## 6. 性能与控制边界

默认生产频率是 10 Hz，允许配置到 20 Hz。1000 台设备同时按 20 Hz 发布时，实时
流量为 20000 条/秒，另有约 1000 条/秒快照。此数字是容量设计目标，不代表已经
通过验收；上线前必须在服务端完成持续 1 小时的 Broker、消费者和 Web 链路压测。

提高实时遥测频率只能让界面更快看到主控箱电机和遥测状态，不会缩短
MQTT 命令路由、MAVLink 下发或设备动作执行时间。实时频率还受 F407 原始消息
上报节拍限制，树莓派不会凭空生成更高频的新状态。

## 7. 运行日志

MQTT 会话创建后，主程序分别打印两个通道的启用状态、实际周期和完整 Topic，不打印
原始 JSON。某通道连续发布失败时只记录第一条警告，恢复成功后若再次失败才重新记录。
