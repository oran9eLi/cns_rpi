# H1/M1 动作去重记录容量修复

日期：2026-10-13

## 原因与影响

H1 与 M1 分别将动作去重记录限制为 128 条。此前 `expiry_ms` 只用于判断新请求是否过期，已完成或已拒绝的历史记录不会回收；达到上限后，新的合法动作在物理执行前返回 `result_uncertain`。现场 H1“基准回显”收到的“动作去重记录已达上限”诊断与该代码路径一致。现场记录文件未被清空或修改；本地复现不等于已读取现场文件逐条核验。

## 修复边界

- H1、M1 在处理新动作时，先核对同一 `action_id` 的重投及跨操作占用，再按当前墙钟时间回收 `expiry_ms <= now` 且已有终态的旧记录。回收与新动作记录由原有原子替换、文件同步及目录同步路径持久化；不增加配置项或修改 MQTT、UART 协议。
- 没有终态的准备/未决记录即使已过期也保留，重启后的相同动作继续返回 `result_uncertain`，绝不盲目重发物理动作。尚未过期的终态仍可按原内容重投；同 ID 改内容仍拒绝。已回收旧动作若再次抵达，原请求的 `expires_at` 已过，只能得到 `action_expired`，不执行串口动作。
- 如果 128 条都不满足回收条件，继续拒绝新增动作，不删除未决记录。时钟尚未到达有效期时也不会提前回收。记录文件仍由程序管理，不提供人工清空作为恢复手段。

## 验证与后续

开发机回归覆盖 H1/M1 各自 128 条已过期终态的满额恢复、混合未过期终态与已过期未决记录、重启后去重及旧请求不重新执行。具体构建和测试结果以本次提交记录为准。尚未部署或修改实体 Pi；需另行安排现场升级与原始 MQTT ACK、Server 数据库结果对照。

Server 端无需新增字段或 Topic，但应保持 `action_id` 全局唯一，不在 `expires_at` 后以新有效期重用旧 ID；已入库的完成事实不能被迟到的 `action_expired` 覆盖。Pi 回收后不再负责恢复该旧终态，Server 应依靠自身持久化事实与既有路由结果收敛。
