# 统一高低频遥测发布通道设计

> 状态：设计已确认，实施尚未开始。本文档描述目标行为，不代表当前运行代码已切换 Topic 或默认频率。

## 1. 背景

当前主程序在 `main.cpp` 中分别维护普通遥测和 PX4 实时遥测的定时、构帧与发布逻辑：

- 普通遥测默认每 1000 ms 发布一次完整 JSON；
- PX4 实时遥测默认每 50 ms 发布一次精简 JSON；
- 两段代码的连接检查、到期判断、发布和时间更新逻辑重复；
- 实时 Topic 名称中包含 `px4`，无法用于主控箱的四路电机状态。

树莓派同一时刻只连接一个受控设备，受控设备可以是 STM32 主控箱或 PX4 飞控。两类设备的数据都已进入同一个 `TelemetryState`，因此发布层不需要按设备类型建立两套框架。

## 2. 目标

1. 将完整快照和实时数据抽象为两个接口一致、发布周期不同的通道。
2. 发布通道只读取最新状态，不为高频遥测建立待发队列。
3. 主控箱的四路电机占空比和 PWM 脉宽可以走实时通道，提高服务端和页面的状态刷新速度。
4. 将 Topic 名称从“设备类型”改为“数据语义”，使主控箱和 PX4 共用同一协议入口。
5. 以 1000 台设备同时在线、每台最高 20 Hz 作为 Broker 容量设计上限。

## 3. 非目标

- 不改变 MQTT 命令下发、MAVLink 组帧、STM32/PX4 执行和 ACK 逻辑。
- 不通过高频遥测实现实时闭环控制。
- 不允许在 `config.json` 中任意指定单个 JSON 字段属于哪个通道；字段归属由版本化的帧构造器确定。
- 不在数据采集端为高低频通道维护两份状态。
- 不保证页面刷新频率高于受控设备的 MAVLink 上报频率。

## 4. Topic 约定

### 4.1 完整快照

```text
{namespace}/{device_id}/telemetry/snapshot/v1
```

- 默认周期：1000 ms（1 Hz）；
- QoS：0；
- retain：false；
- 内容：当前完整遥测 JSON，包含设备基本状态、慢变字段、模块、告警、日志、5G 链路和身份附加信息；
- 服务端用途：维护设备最新快照，必要时写入数据库。

### 4.2 实时遥测

```text
{namespace}/{device_id}/telemetry/realtime/v1
```

- 默认周期：100 ms（10 Hz）；
- 允许范围：50–1000 ms（1–20 Hz）；
- QoS：固定为 0；
- retain：固定为 false；
- 失败策略：丢弃当前帧，不重传、不追帧；
- 服务端用途：页面按设备订阅并展示最新帧，不写入设备状态数据库。

Topic 使用 `snapshot/realtime` 而不使用 `slow/fast` 或 `px4`。前者表示数据语义，不会因配置频率或受控设备类型变化而失真。

### 4.3 旧 Topic 处理

新协议不保留以下旧 Topic 的双发兼容层：

```text
{namespace}/{device_id}/telemetry
{namespace}/{device_id}/px4/realtime/v1
```

这是一次协议破坏性变更。部署时先让服务端订阅新 Topic，再升级树莓派；全部设备升级后删除服务端的旧订阅。树莓派不同时发布新旧两套遥测，避免 Broker 流量翻倍。

## 5. 发布通道抽象

### 5.1 责任边界

新增独立的遥测发布调度模块，从 `main.cpp` 移出两段重复定时逻辑。模块不负责 MQTT 连接、身份学习、MAVLink 解码或状态存储。

单个通道包含以下固定属性：

```cpp
struct PublishChannelOptions {
  std::string name;
  std::string topic;
  std::chrono::milliseconds interval;
  int qos;
  bool retain;
};
```

每个通道对外提供相同的到期判断和发布入口，并持有自己的上次发布时间。帧构造器作为明确依赖注入，不由 `MqttClient` 根据 Topic 反向推断。

```cpp
using FrameBuilder = std::function<nlohmann::json(
    const state::TelemetryState&, std::uint64_t sequence)>;
```

`MqttClient` 继续只负责将已构造的字节发送到指定 Topic，不感知高低频、设备类型或 JSON 字段。

### 5.2 调度流程

1. 主循环完成串口接收、MAVLink 解码和 `TelemetryState` 更新。
2. MQTT 已连接、当前 `device_id` 与 MQTT 会话身份一致时，调用发布调度器。
3. 调度器检查两个通道是否到期。
4. 至少一个通道到期时才读取一次最新状态快照；同一轮中两个通道都到期时共用该快照。
5. 各通道使用自己的帧构造器筛选字段、构造 JSON 并发布。
6. 无论高频帧发布成功与否，本次节拍都已消耗；下一节拍只发送届时的最新状态。

该设计中的“两辆公交车”是两个定时采样发布器，不是两个先进先出队列。不保存历史帧是防止断网或慢消费者将实时链路变成延迟链路的关键。

## 6. JSON 字段分组

### 6.1 快照帧

快照帧继续输出当前完整遥测结构，包含实时帧中的动态字段。服务端因此无需依赖实时 Topic 才能获得完整设备快照。

### 6.2 实时帧

实时帧顶层至少包含：

```json
{
  "schema_version": 1,
  "device_id": "DCDWCNS1...",
  "sequence": 42,
  "sent_at": "2026-08-04T08:00:00.123Z",
  "telemetry": {}
}
```

实时帧使用每个 MQTT 设备会话独立、单调递增的 `sequence`。重新连接受控设备或重建 MQTT 会话时可以从 0 重新开始，消费者不得将其当作跨会话持久序号。

精简字段集合为：

- 主控箱动态字段：`motor.duty_percent`、`motor.pwm_us`、`motor.pwm_time_usec`、`motor.run_state`、`motor.speed_level`；
- 飞控动态字段：`heartbeat`、`attitude`、`gps`、`global_position`、`sys_status`、`battery`、`pressure`；
- 尚未收到的字段不输出，不用 `null` 占位；
- 同一设备如同时具有上述两类动态数据，实时帧可同时携带，发布层不按 `device_type` 人为丢弃已收到的字段。

实时帧不携带 `school_name`、`dcdw_label`、`modules`、`alarms`、`logs`、`drone_id`、`cellular_5g` 等慢变或较大字段。

### 6.3 电机状态的“跟手”边界

将 `motor` 放入实时帧后，在固件上报频率不低于 10 Hz 的前提下，树莓派到服务端的状态刷新间隔可从约 1 s 缩短至约 100 ms。

该改动不会缩短以下环节：

- MQTT 控制命令到达树莓派的时间；
- 树莓派将命令转换为 MAVLink 并写入串口的时间；
- STM32 执行动作的时间；
- 固件本身的电机状态采样和上报周期。

## 7. 配置

两个通道在配置中采用对称结构：

```json
{
  "telemetry_publish": {
    "snapshot": {
      "enabled": true,
      "interval_ms": 1000
    },
    "realtime": {
      "enabled": true,
      "interval_ms": 100
    }
  },
  "mqtt": {
    "topics": {
      "telemetry_snapshot": {
        "suffix": "telemetry/snapshot/v1",
        "qos": 0
      },
      "telemetry_realtime": {
        "suffix": "telemetry/realtime/v1",
        "qos": 0
      }
    }
  }
}
```

配置校验规则：

- `snapshot.interval_ms`：100–60000 ms；
- `realtime.interval_ms`：50–1000 ms；
- Topic suffix 不得为空，两个 suffix 不得相同；
- 实时通道的 QoS 必须为 0；
- 两个通道的 retain 均由程序固定为 false，不开放配置。

旧 `runtime.telemetry_publish_interval_ms` 和 `px4_realtime` 配置段在本次协议升级后删除，不实施运行时双解析。部署脚本在覆盖新版程序前必须迁移现场 `config.json`；配置命令中现有的 `telemetry_publish_interval_ms` 继续表示快照通道周期，配置更新器将其写入 `telemetry_publish.snapshot.interval_ms`，避免破坏已有服务端命令协议。本轮不新增远程修改实时通道频率的命令字段。

现场迁移时，旧 `px4_realtime.publish_interval_ms=50` 视为上一版默认值并迁移为新默认 100 ms；其他合法的显式周期原样保留。这保证普通升级后默认以 10 Hz 运行，同时不覆盖现场主动设置的其他频率。

## 8. 设备类型行为

- 快照通道对主控箱和 PX4 都启用。
- 实时通道不再以 `device_type == flight_controller` 作为硬编码条件。
- 实时通道是否工作只由 `telemetry_publish.realtime.enabled` 与 MQTT/身份就绪状态决定。
- 帧构造器对缺失字段做省略处理，因此主控箱实时帧可以只含 `motor`，PX4 实时帧可以只包含飞行动态字段。

## 9. 异常和恢复

- MQTT 未连接或身份未就绪：不构造、不缓存遥测帧。
- MQTT 发布调用失败：记录限频警告，消耗当前节拍，等待下一节拍。
- 串口断开：现有串口重发现逻辑负责恢复；断开期间不反复发布陈旧实时帧。
- 程序重启或受控设备切换：重置两个通道的调度时间和实时 `sequence`，使新会话不继承旧设备节拍。
- 服务端或 Web 消费速度不足：只保留每台设备的最新实时帧，丢弃旧帧，不得将高频 Topic 接入无界队列。

## 10. 1000 台设备容量约束

### 10.1 消息规模

极限工况为：

```text
1000 台 × 20 帧/秒 = 20000 条实时消息/秒
1000 台 × 1 帧/秒  =  1000 条快照消息/秒
```

默认生产频率为 10 Hz，20 Hz 只是可配置上限和容量验收工况。

### 10.2 Broker 和消费者限制

- 实时帧使用 QoS 0、`retain=false`，不产生 Broker 持久化和重传压力。
- 数据库维护服务只订阅 `+/telemetry/snapshot/v1`，不订阅实时 Topic。
- Web 实时服务只订阅当前有用户查看的设备，禁止常驻订阅 `+/telemetry/realtime/v1` 后再做应用层全量筛选。
- Broker 和 WebSocket 转发层的每设备实时队列必须有界，最多保留最新一帧。
- 快照、注册、配置和控制 Topic 的处理资源不得被实时流量共享队列耗尽。

### 10.3 容量验收

在正式生产 Broker 硬件和配置上运行 1000 个模拟设备，每台持续发布 20 Hz 实时帧和 1 Hz 快照帧，持续至少 1 小时。验收条件为：

1. Broker 无崩溃、无 OOM、无自动重启；
2. 内存和待发队列在预热后无持续单调增长；
3. Broker CPU 在压测期间持续占用不高于 80%，网络带宽不高于物理链路容量的 70%；
4. 不因 Broker 过载造成设备集中断线或 MQTT 会话反复重连；
5. 快照消费链路在高频压力下仍可持续收到每台设备的最新快照；
6. 单设备 Web 实时订阅不出现随运行时间持续增长的延迟。

任一容量条件不满足时，先将默认实时频率从 10 Hz 降为 5 Hz，不通过增加设备侧队列或改用 QoS 1 掩盖消费能力不足。

## 11. 日志

启动时仅打印两个通道实际应用的启用状态、周期和 Topic，例如：

```text
遥测快照通道: 已启用 周期=1000ms topic=cns_rpi/{device_id}/telemetry/snapshot/v1
遥测实时通道: 已启用 周期=100ms topic=cns_rpi/{device_id}/telemetry/realtime/v1
```

不按帧打印实时 JSON。发布失败日志必须限频，避免 Broker 或网络故障时按 10–20 Hz 写满日志。

## 12. 测试与验收

### 12.1 单元测试

- 两个通道使用同一类型、不同周期时的到期判断。
- 同一轮两个通道到期时共用一份状态快照。
- 发布失败后不在下一轮立即补发旧帧。
- 实时帧包含主控箱 `motor` 字段，不包含模块、告警、日志、5G 和 Remote ID 字段。
- 实时帧继续包含已实现的 PX4 动态字段。
- 配置边界、空 Topic、重复 Topic 和实时 QoS 非 0 均被拒绝。
- 旧配置命令参数正确更新快照通道周期。

### 12.2 集成测试

- 主控箱连接时，两个新 Topic 均有消息，实时 Topic 的 `motor` 以配置节拍刷新。
- PX4 连接时，两个新 Topic 均有消息，实时 Topic 保持原有飞行动态字段。
- 网络断开后重连，不会在恢复瞬间补发断网期间的历史帧。
- 服务端数据库维护逻辑只消费快照 Topic，Web 实时逻辑只按需消费实时 Topic。
- 进行第 10.3 节规定的 1000 设备压力验证。
