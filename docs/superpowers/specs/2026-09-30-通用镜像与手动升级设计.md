# 树莓派通用镜像与手动升级设计

状态：设计已在对话中确认，尚未实施。本文只约束树莓派首次部署与应用升级；`mavlink-router` 双路转发另行设计。

## 1. 目标与边界

一张镜像可用于不同学校的新 Raspberry Pi 5。制作启动盘时输入学校名；烧录完成、接入箱内 F407 和既定网络后，不必登录树莓派执行安装或构建命令。镜像自带一个可运行的稳定版本，首次启动不依赖在线下载。后续由维护人员在树莓派上主动执行命令，从可配置的 CNS Server 地址安装已发布版本；不设置自动检查、自动安装或定时任务。

首版只升级树莓派应用、配套脚本、配置 helper 和 systemd 服务文件，不升级 Raspberry Pi OS、内核、系统软件包或分区。发布包若不兼容镜像中已有的系统依赖，应拒绝安装并提示制作新版镜像。Server 只暂存并提供静态版本清单与发布包，不保存设备升级状态、不向设备推送升级，也不负责回滚。

不修改 F407 固件，不要求 F407 提供学校名。F407 与 Pi 在同一箱内配套使用；Pi 继续从自身配置读取学校名用于注册和遥测，设备业务身份仍来自 F407 的 `OPEN_DRONE_ID_BASIC_ID.uas_id`。不在本设计中接入 `mavlink-router`、改变串口所有权或实现服务器 5760 透传。

## 2. 当前基线与需要改变的地方

当前新设备需创建 `dcdw` 用户、克隆仓库、填写 `config/config.json`、运行 `scripts/install_deps.sh`。`scripts/deploy.sh` 在 `/home/dcdw/cns_rpi/build` 原地构建，交互取得 sudo 权限，安装两个服务并重启；它没有版本化安装目录、升级后稳定运行判定或自动回滚。`cns-rpi.service` 和 `cellular-dialup.service` 的执行路径指向该仓库。运行配置固定在 `/var/lib/cns-rpi/config.json`，身份绑定另存于 `/var/lib/cns-rpi/device_binding.json`。

镜像交付将预装依赖、已构建的稳定版程序、配置 helper、两个自启动服务和升级命令。服务执行路径改为版本化安装目录的稳定入口，不能继续依赖仓库中的 `build/` 产物；源码部署脚本保留供开发或维护使用，不作为升级器的实现。现有配置写入、设备身份绑定、5G 守护服务与主程序互不阻塞的运行语义保持不变。

## 3. 通用镜像与学校名写入

镜像基于 Raspberry Pi OS Lite 64 位、项目当前目标系统 trixie / Debian 13，使用 `pi-gen` 的 ARM64 构建流程和仓库内可重复运行的定制阶段生成；不从已投入运行的设备直接复制整盘作为交付品。构建结果记录操作系统基线、应用版本、构建提交及镜像哈希。镜像中不放学校名、现场密码、私钥、已绑定的 `device_id`、设备运行日志或从样机复制的机器标识；新设备首次启动后须具有独立的系统机器标识和 SSH 主机密钥。

烧录工具接收镜像、目标启动盘和非空学校名，先明确展示目标盘并要求操作者确认覆盖，再写入镜像及校验。烧录后把仅含部署所需非秘密参数的首次配置文件写入启动分区，至少包含配置格式版本和 `school_name`；更新服务器基础地址可在同一步设置，不设置时采用镜像构建时提供的默认地址。工具不得把学校名或下载地址重新编译进应用或生成每校专属镜像。

首次启动的初始化步骤在业务服务启动前读取并校验首次配置，依据镜像内通用配置模板建立 `/var/lib/cns-rpi/config.json`，将学校名写入 `identity.school_name`，并写入独立的升级器配置。必须校验配置完整性及学校名非空，禁止把仓库样例中的 `SEU` 当作缺省学校。输入缺失或无效时，不允许主程序以错误学校名注册；记录明确错误并等待维护人员修正。已有合法现场配置不被首次初始化重复覆盖，重复启动保持幂等。初始化完成后，`cellular-dialup.service` 与 `cns-rpi.service` 仍互不等待网络或 F407 在线。首版以现行无需设备专属 MQTT 凭据的接入方式为前提；若将来引入每机密钥，须另行设计安全灌装，不能把秘密放进可直接读取的启动分区。

设备绑定文件在镜像内不存在；首次连接箱内 F407 后继续由现有身份核验逻辑建立绑定。学校名与设备业务身份是不同字段，烧录工具不生成、猜测或改写 `device_id`。

## 4. 发布与暂存

GitHub 发布流程在与目标系统兼容的 ARM64 构建环境生成应用发布包，运行自动化测试，并输出版本、目标架构、系统兼容基线、包大小和 SHA-256 摘要。发布包至少包含主程序、5G 脚本、配置 helper、两个 systemd 单元及升级所需的版本元数据；不得包含现场 `config.json`、设备绑定、密码或私钥。产物还须在目标 Raspberry Pi OS 基线上验证能加载其运行时依赖。

CNS Server 在可配置的基础地址下存放不可变的 `releases/<version>/` 版本包，并提供 `current.json` 静态清单。清单至少含格式版本、发布版本、目标架构、目标系统基线、包相对路径、字节数和 SHA-256；包路径必须位于同一基础地址下，禁止清单指向任意外部站点。发布顺序为先完整上传并核对包，再原子更新 `current.json`；Pi 不以 GitHub 为下载入口，也不把每个新 Git Tag 自动视作可安装版本。基础下载地址由 Pi 升级器配置决定，可在首次烧录时设置，后续由维护人员修改。首版不修改 `cns_server` 仓库，不要求 Server 新增设备升级 API、调度器或数据库表；交付静态文件布局和上架步骤供 Server 维护人员执行。

首版不加入发布签名、公钥管理或产物证明校验。Pi 必须检查下载长度和清单所列 SHA-256，以发现传输损坏；这不能证明发布者身份，信任边界是配置的 CNS Server 及其传输通道。该限制作为已接受的首版风险记录，后续若要开放无人值守或扩大分发范围，再单独评估签名和传输保护。

## 5. 手动升级事务

维护人员执行 `cns-upgrade check` 查看可安装版本，执行 `cns-upgrade install` 安装清单指向的版本，执行 `cns-upgrade rollback` 返回上一个已安装版本。命令提供当前版本、目标版本、进度和最终结果；不在后台定时运行。需要写系统路径时使用交互式 sudo 授权，不要求设备配置免密 sudo；无权限应明确失败，不进入半安装状态。

安装按以下顺序进行：

1. 读取升级器配置和静态清单，检查版本、ARM64 架构、系统基线及包的允许范围；无网络、信息不完整或不兼容时保持当前版本。
2. 将整个包下载到本地暂存位置，核对大小与 SHA-256；只接受预期路径与文件类型，拒绝归档越界写入。下载期间不停止业务服务。
3. 展开至 `/opt/cns-rpi/releases/<version>/` 下新的、不可变且由 root 管理的版本目录，运行候选程序的版本检查和针对现有现场配置的 `--check-config`。首版升级器不自动迁移配置结构；候选程序不兼容现有配置时拒绝安装。
4. 保留上一版完整程序目录，以及可能变化的 root 所有配置 helper 和 systemd 单元副本；在本地完成所有准备后才停止受影响服务、切换 `/opt/cns-rpi/current` 稳定入口、收敛 helper 和单元文件、重新加载 systemd 并启动服务。两个服务从此入口加载程序与脚本；提权用的配置 helper 继续保持 root 所有的固定执行路径，不能指向 `dcdw` 可写文件。升级包不得覆盖 `/var/lib/cns-rpi` 中的现场配置与设备绑定。
5. 检查实际运行版本、两个单元已启用，以及主程序在连续 60 秒观察窗口内持续运行、两个服务均未出现重启循环。观察窗口超过主程序当前 30 秒的 systemd watchdog 超时。MQTT、5G 数据链路和 F407 可以暂时离线，不作为升级成功的必要条件。
6. 切换或启动检查失败时，在本机恢复上一版程序、helper、单元文件及稳定入口，重新加载 systemd 并启动旧服务，明确记录失败和回滚结果。手动 `rollback` 沿用同一恢复机制。

升级事务不能因 Server 在下载完成后不可用而失去本地回滚能力。`cns-upgrade` 不调用 `deploy.sh` 重新编译；镜像和升级器运行所需依赖应已安装。首版升级器本身作为镜像内的独立维护工具，不通过自己的 `install` 命令自更新；其接口或信任规则需要改变时另行评审。不能安全迁移的系统依赖变更由新版镜像交付，不以应用升级命令隐式执行 `apt`。

## 6. 验收与交接

镜像验收至少使用全新启动盘和未配置的 Raspberry Pi：不同学校名的两次烧录产生同一镜像版本但不同的现场配置；首次启动、断电重启后两个服务均保持自启动；无学校名不能注册为样例学校；每台机器的系统标识、SSH 主机密钥和设备绑定互不复制。F407 接入后仍由真实 Basic ID 建绑，现有注册、遥测、5G 和实验行为不得退化。

升级器自动化测试至少覆盖清单与包校验、目标系统不兼容、配置不兼容、下载中断、归档路径越界、无 sudo 权限、重复安装、正常安装、启动失败自动回滚、人工回滚，以及现场配置和身份绑定逐字节保留。实体 Pi 验收需在可回退的维护窗口完成成功升级和故障注入；只检查 `systemctl is-active` 的瞬时结果不能算作稳定运行验证。

交付时同步 README、新设备部署手册、示例配置、发布说明和变更记录，说明镜像烧录、学校名输入、升级命令、Server 静态文件准备、现场验证及回滚步骤。测试报告分别标明本地、ARM64 构建与实体 Pi 的结果；未经单独授权不部署到现场设备。
