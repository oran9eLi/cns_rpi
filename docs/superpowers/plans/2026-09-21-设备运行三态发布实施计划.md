# 设备运行三态发布实施计划

> **执行要求：** 实施时必须使用 `superpowers:executing-plans`，在独立工作树和 `codex/` 前缀分支中逐项执行；每项任务先写失败测试，再实现最小代码使其通过。

**目标：** 在不修改 Server/Web/F407 协议、不开始阶段一实验或 QGC 透传的前提下，让 CNS 主控箱树莓派端以 QoS 1、retained 发布已冻结的运行三态，并通过 Last Will 准确表达 Pi 控制链离线。

**架构：** 新增一个仅服务于运行三态的小模块，集中承担枚举、合法组合、JSON、10 秒业务静默计时和“变化/重连才发布”决策，不扩展成通用状态框架。设备绑定用独立小文件原子持久化；主程序保留 MQTT 会话与串口链路两条独立生命周期，串口失联只改变业务/身份事实，不再关闭 MQTT。

**技术栈：** C++23、CMake/CTest、doctest、nlohmann/json、libmosquitto、`std::chrono::steady_clock`、原子文件替换。

**权威契约：**

- `docs/2026-09-20-新版设备接入基线契约.md`
- `docs/2026-09-20-阶段一树莓派与主控板任务交接清单.md`

## 一、已核对的现状

### 仓库与工作区

- 当前分支为 `main`，`HEAD=f0026a30badc311f938512a674f3896387556605`，标记为 `v1.0.0`，与 `origin/main` 一致。
- 工作区已有用户未提交改动：`README.md`、`docs/V1设计文档.md` 和 4 份未跟踪文档。实施期间不得覆盖、暂存、删除或顺手提交这些改动。
- 仓库中未找到 `AGENTS.md`；已完整阅读 `README.md`、`docs/协作规则.md` 和两份权威契约。

### 现有能力

- `src/main.cpp:600-717` 只有当前串口会话已获得 `device_id` 和 `device_type` 时才创建 MQTT 客户端。
- schema v3 registration、两个遥测 Topic、配置命令和主控箱私有控制命令已共用同一条 MQTT 连接。
- `registration::RegistrationState` 已具备“连接上升沿强制重发、成功后才清除待发状态”的行为，可借鉴但不能替代运行三态。
- `MqttClient` 支持在连接前设置一条 Last Will，并可通过 `IsConnected()` 观察自动重连结果。
- `MavlinkFrameAssembler` 只交付通过 CRC 校验的完整帧；现有遥测与扩展解码器会返回是否识别并写入业务状态。

### 现有代码与契约的差异

1. **串口生命周期与 MQTT 耦合。** `src/main.cpp:267-280` 在串口失败时关闭 MQTT，`src/main.cpp:509-512` 在 10 秒无合法 MAVLink 帧时也走同一路径。F407 失联会让 Pi 控制链同时离线，无法形成 `online|offline|...`，也不能继续接收 MQTT 命令。
2. **没有持久化绑定。** `state::StateStore` 中的 `device_id` 仅在内存中，`ResetDeviceState()` 会全部清空。重启后不能产生 `cached`，也不能在 F407 静默时恢复 MQTT 控制入口。
3. **Last Will 目标不同。** `src/main.cpp:635-654` 当前把 MQTT 连接唯一的 Last Will 配置为 registration offline；新契约要求该遗嘱发往 runtime Topic。
4. **身份冲突会重新识别。** `src/main.cpp:417-425` 当前关闭旧会话并清空身份，可能切换到冲突设备 Topic，与“不得自动改绑”冲突。
5. **缺少三态协议与配置。** `MqttTopicsConfig`、示例配置、topic 构造器、测试和文档均没有 runtime status。

### 最小处理建议（随本计划一并确认）

- 保留一条 MQTT 连接，将其唯一 Last Will 从 registration offline 改为契约规定的 runtime offline。registration 仍在连接/重连后主动发布 online，正常退出时主动发布 offline；异常断线由独立 runtime retained 消息表示控制链离线。
- 不建立第二条 MQTT 连接来模拟“两条遗嘱”，避免两条连接部分断开时误报控制链状态。
- 绑定缓存只保存真实 `OPEN_DRONE_ID_BASIC_ID.uas_id` 验证得到的 `device_id` 及已识别的 `device_type`；不提供 Web/API 换绑、自动换绑或多设备选择。
- “有效业务帧”以已通过 CRC、来自已识别 F407 端点、且被现有遥测/主控箱扩展解码器识别为业务数据的帧为准；身份帧、`COMMAND_ACK`、未识别帧和 Pi 主动发送帧不刷新业务计时。

## 二、实施任务

### 任务 1：固化运行三态协议、合法组合和发布决策

**预计提交：** `feat: 增加设备运行三态模型`

**文件：**

- 新建 `src/runtime_status/runtime_status.hpp`
- 新建 `src/runtime_status/runtime_status.cpp`
- 修改 `src/mqtt/topic.hpp`、`src/mqtt/topic.cpp`
- 新建 `tests/test_runtime_status.cpp`
- 修改 `tests/test_mqtt_topic.cpp`、`CMakeLists.txt`

**先写失败测试：**

1. Topic 精确为 `{namespace}/{device_id}/runtime/status/v1`，发布选项固定为 QoS 1、`retain=true`。
2. `online|online|verified` JSON 只有五个契约字段，`schema_version` 为整数 1，不存在 `vendor_id` 或别名。
3. 有绑定和无绑定分别生成 `offline|unknown|cached`、`offline|unknown|unbound` 两种合法 Last Will。
4. 模型拒绝 `offline|online|...`、`offline|offline|...`、`offline|unknown|verified/conflict` 等非法组合。
5. 持续有效业务帧保持 online；距最后一帧满 10 秒时只转为 offline；新帧立即恢复 online。
6. 有缓存未复核、身份一致、身份冲突、无绑定分别得到 `cached/verified/conflict/unbound`。
7. 三态不变时不重复发布；MQTT 连接上升沿即使内容不变也强制发布；失败时保留待发状态。

**最小实现：**

- 定义三个枚举、一份快照和固定协议常量，只提供契约规定的取值。
- 用 `steady_clock` 管理初始 unknown、最后业务帧和固定 10 秒阈值，不增加配置项或周期心跳。
- 只把“内容变化”和“MQTT 连接上升沿”作为发布触发条件，成功后才记录已发快照。
- 只为 `cns_box` 启用运行三态，不给真实飞控伪造 F407 状态。

**验证：**

```bash
cmake --build build --target test_runtime_status test_mqtt_topic -j2
ctest --test-dir build -R '^(runtime_status|mqtt_topic)$' --output-on-failure
```

### 任务 2：增加最小设备绑定持久化

**预计提交：** `feat: 增加设备身份绑定缓存`

**文件：**

- 新建 `src/device/device_binding_store.hpp`、`src/device/device_binding_store.cpp`

- 修改 `tests/test_app_config.cpp`、`config/config.example.json`、`CMakeLists.txt`

**先写失败测试：**

1. 缓存不存在时返回“未绑定”，不伪造 `device_id`。
2. 只接受固定 schema、合法 `device_id` 和 `device_type=cns_box`；破损 JSON、非法 ID、未知类型均返回明确错误。
3. 首次建绑先完整写候选文件再原子替换；失败时不留下半截绑定。
4. 相同身份只核验一致性，不反复改写；不同身份返回冲突且原文件不变。
5. 配置中的绑定路径必须为绝对路径；老配置缺少字段时默认 `/var/lib/cns-rpi/device_binding.json`。

**最小实现：**

- 绑定文件只保存 schema、`device_id`、`device_type`，不保存在线状态、串口号、机器身份或服务器字段。
- 路径使用 `identity.binding_file`；示例采用 `/var/lib/cns-rpi/device_binding.json`，字段可选以兼容已部署的旧配置。
- 加载失败按未绑定处理并记录中文告警；首次持久化失败时不得声称 `verified`。

### 任务 3：解耦 F407 串口与 MQTT 控制生命周期

**预计提交：** `refactor: 解耦串口与MQTT控制生命周期`

**文件：**

- 修改 `src/main.cpp`
- 按可测性最小新增 `src/runtime_status/device_session.hpp`、`src/runtime_status/device_session.cpp`
- 新建 `tests/test_device_session.cpp`
- 修改 `CMakeLists.txt`

**先写失败测试：**

1. 有合法缓存时，本次启动尚未收到 F407 身份帧前为 `cached`，并能用缓存 `device_id` 创建 MQTT 控制会话。
2. 无缓存时不生成、不从配置猜测 `device_id`；只在收到真实合法 F407 Basic ID 后建绑。
3. 串口读写失败或 10 秒静默只清理串口端点和瞬时遥测状态，不关闭 MQTT、不删除绑定、不丢失命令订阅。
4. 串口断开时，F407 控制命令返回现有 `device_link_unavailable`；Pi 本地配置命令仍可继续走 MQTT 流程。
5. 新 F407 身份与缓存一致时转为 `verified`；不一致时转为 `conflict`，保持原 Topic 和原绑定，不上传冲突设备遥测，也不向冲突设备下发控制命令。
6. 运行三态发布失败后，registration、入站命令、串口发现/接收和遥测调度仍可继续执行。

**最小实现：**

- 将“释放串口链路”和“关闭 MQTT 会话”拆为两个操作；串口失败和静默看门狗只执行前者。
- 启动先加载绑定；有缓存就先恢复 MQTT 控制入口，同时继续串口发现和身份复核。
- 当前串口身份与持久化绑定分开保存；遥测状态重置不删除绑定。
- 只有身份已验证一致且有当前串口业务事实时才发布遥测，避免断链后重复旧快照或把冲突设备数据挂到缓存 Topic 下。
- 首次持久化失败时保持 `unbound` 并记录中文错误，不把临时内存身份冒充为已持久化绑定。

**验证：**

```bash
cmake --build build --target test_device_session test_control_transaction test_registration_state test_telemetry_publisher -j2
ctest --test-dir build -R '^(device_session|control_transaction|registration_state|telemetry_publisher)$' --output-on-failure
```

### 任务 4：接入 runtime Topic、Last Will 和事件驱动发布

**预计提交：** `feat: 接入设备运行三态发布`

**文件：**

- 修改 `src/main.cpp`
- 仅在测试确有需要时最小修改 `src/mqtt/mqtt_client.hpp`、`src/mqtt/mqtt_client.cpp`
- 修改 `tests/test_mqtt_client.cpp`、`tests/test_runtime_status.cpp`、`tests/test_main_logging_contract.cpp`

**先写失败测试：**

1. `ConnectionOptions.will` 收到 runtime Topic、QoS 1、`retain=true` 和基于绑定事实生成的合法离线载荷，且仍在连接 Broker 前设置。
2. MQTT 首次连接和每次重连后，强制发布当前 `control_status=online` retained 状态，覆盖旧离线遗嘱。
3. 发布失败输出明确中文日志并保留待发状态；断线期间不忙等待，重连后重发。
4. 同一快照在连接持续正常时，不因主循环或遥测周期重复发布。
5. 三态发布失败后，registration、入站队列、串口处理和遥测 `Tick()` 均不被跳过或终止。
6. 正常退出时有界发布 runtime offline，再保留现有 registration offline 主动发布；异常终止只由 Broker 交付 runtime Last Will。

**最小实现：**

- 在主程序拼接 runtime Topic，用运行三态模块构造 Last Will，替换当前 registration Last Will。
- 每轮主循环只做一次非阻塞三态发布决策；失败只记录日志，不 `return`、不 `break`、不关闭其他链路。
- 不改动 registration payload、snapshot/realtime payload、命令 Topic 或 Server/Web 字段。
- 日志仅在状态变化、连接/重连强制发布、发布失败和失败恢复时输出，不按主循环刷屏。

**验证：**

## 三、真机验收步骤（只写文档，本轮不执行）

1. 正常启动 Pi 和 F407，新订阅者订阅 `{namespace}/{device_id}/runtime/status/v1`，验证立即收到 retained `online|online|verified`。
2. 停止或断开 F407 业务超过 10 秒，验证只变为 `online|offline|<真实身份状态>`；用无副作用控制请求或配置查询证明 MQTT 控制入口仍可达。
3. 恢复原 F407，验证新有效业务帧和一致身份使三态回到 `online|online|verified`。
4. 非正常终止 Pi 进程或断开 Pi 网络，验证 Broker 发布 retained `offline|unknown|cached`；仅在专门的空绑定环境验证 `offline|unknown|unbound`。
5. 恢复 Pi 网络或进程，验证重连主动发布的当前 online 三态覆盖 retained 离线遗嘱。
6. 向 Server 端交付同一时间线的 MQTT 原始 Topic/载荷、Pi 中文日志、数据库记录、REST 响应、WebSocket 事件和 Web 页面状态，核对六者一致。
