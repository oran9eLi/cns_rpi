# 设备运行三态发布与验收

日期：2026-09-21

本文说明树莓派端“新版设备接入基线”的主控箱运行三态、固定身份绑定、部署回滚和跨端验收方法。本文只覆盖当前 F407 主控箱，不扩展 PX4、实验 Session、QGC 或原始 MAVLink 透传。

## 1. Topic 与载荷

主控箱发布 Topic：

```text
{namespace}/{device_id}/runtime/status/v1
```

- QoS：1；
- Retain：true；
- 不增加固定周期心跳；
- 三态任一字段变化时立即发布；
- MQTT 每次成功连接或重连后，即使值未变化也重新发布当前在线状态，覆盖上一次异常断线留下的 retained 遗嘱。

载荷只能包含以下五个字段：

```json
{
  "schema_version": 1,
  "device_id": "DCDWCNS1EXAMPLE00001",
  "control_status": "online",
  "business_status": "online",
  "identity_status": "verified"
}
```

字段语义：

- `control_status=online|offline`：只表示 Pi 到 MQTT Broker 的控制链是否可达；
- `business_status=online|offline|unknown`：只表示 F407 最近是否持续提供有效业务帧；
- `identity_status=verified|cached|conflict|unbound`：只表示当前 F407 身份与本机持久化绑定的核验结果。

registration 与运行三态互不改写。registration 继续声明设备类型、稳定元数据和其既有在线状态；Server/Web 判断 Pi 控制链、F407 业务链和身份核验时必须读取 runtime 状态，不能用其中一个代替另一个。

## 2. 状态来源与变化规则

### 2.1 控制链

MQTT 已连接时，正常发布的 `control_status` 固定为 `online`。Pi 异常断线后由 Broker 交付 Last Will，表达 `offline`。正常退出时程序先有界发布 runtime 离线状态，再发布 registration 离线状态。

### 2.2 F407 业务链

有效业务帧必须同时满足：MAVLink CRC 校验通过、来自已识别的 F407 端点，并被现有标准遥测或主控箱扩展解码器识别。现有标准遥测（包括 HEARTBEAT）及可识别的 `NAMED_VALUE_INT`、`TUNNEL` 会刷新业务时间；身份帧、`AUTOPILOT_VERSION`、`COMMAND_ACK`、未知帧及 Pi 主动发送帧不刷新。

- 启动后尚无业务事实时为 `unknown`；
- 收到有效业务帧后立即变为 `online`；
- 距最后一条有效业务帧满 10 秒后变为 `offline`；
- 新有效业务帧到达后立即恢复为 `online`。

串口读写失败、USB 重新枚举或 10 秒静默只清理串口端点和瞬时遥测，不关闭已由主控箱绑定恢复的 MQTT 控制入口。重新收到 HEARTBEAT 只证明链路端点存在，不能继承旧链路的身份核验资格；必须收到与缓存一致的新 Basic ID 后才恢复主控箱控制和遥测。此时配置命令仍可接收；主控箱控制命令返回链路不可用或身份未核验，不向不确定设备发送。身份未核验或冲突期间的普通业务帧不写入共享遥测缓存。

### 2.3 身份核验

- `verified`：当前真实 Basic ID 与持久化绑定一致；
- `cached`：存在合法缓存，但本次启动尚未重新取得匹配的真实身份；
- `conflict`：当前真实身份与缓存冲突；保持原 Topic 和原绑定，不上传冲突设备遥测，也不向其下发主控箱命令；
- `unbound`：从未成功持久化合法身份。

## 3. 身份绑定文件

默认路径为 `/var/lib/cns-rpi/device_binding.json`，可通过 `identity.binding_file` 指定。示例配置已经包含该路径，启动日志会打印实际应用路径。

文件只保存固定配对事实，不保存在线状态、串口设备号、MAVLink sysid/compid、遥测或 MQTT 状态：

```json
{
  "schema_version": 1,
  "device_id": "DCDWCNS1EXAMPLE00001",
  "device_type": "cns_box"
}
```

首次没有绑定时，程序只接受真实且合法的 F407 Basic ID，并以临时文件加原子重命名方式建绑；配置文件不能预填或猜测 `device_id`。首次候选落盘失败后不会接受另一个身份替换该候选，落盘结果也必须与当前观测身份一致。重启时合法缓存用于恢复原设备 MQTT Topic，但不代表 F407 在线。真实身份重新出现后必须核对；冲突不会覆盖文件。若 unbound 会话运行期间绑定由失败转为成功，程序会有界重建 MQTT 连接，使 Broker 保存的 Last Will 从 `unbound` 更新为 `cached`。

只有维修更换固定配对的 F407 时，维护人员才可在现场停止服务、备份并清除绑定：

```bash
sudo systemctl stop cns-rpi.service
sudo cp -a /var/lib/cns-rpi/device_binding.json \
  /var/lib/cns-rpi/device_binding.json.bak
sudo rm /var/lib/cns-rpi/device_binding.json
sudo systemctl start cns-rpi.service
```

清除后必须从新 F407 的真实 Basic ID 重新建绑。不得把此操作做成远程自动换绑、普通用户按钮或冲突自动恢复逻辑。

## 4. MQTT Last Will

主控箱在发起 Broker 连接前设置与正常三态相同 Topic、QoS 1、`retain=true` 的 Last Will。遗嘱只表达 Pi 控制链离线：

```json
{
  "schema_version": 1,
  "device_id": "DCDWCNS1EXAMPLE00001",
  "control_status": "offline",
  "business_status": "unknown",
  "identity_status": "cached"
}
```

从未成功持久化身份时，`identity_status` 使用 `unbound`。遗嘱禁止使用 `business_status=offline`、`identity_status=verified` 或 `identity_status=conflict`，因为 Pi 断线后 Server 无法继续判断 F407 实时事实。

运行三态发布使用非阻塞发布接口。单次发布失败只记录一次中文警告并保留待发状态；后续连接恢复后重发并记录恢复，不中断 registration、入站命令、串口发现/接收或遥测调度。

## 5. 升级与配置检查

升级前记录当前提交并备份现场配置和绑定文件：

```bash
cd /home/dcdw/cns_rpi
git rev-parse HEAD
sudo cp -a /var/lib/cns-rpi/config.json /var/lib/cns-rpi/config.json.bak
sudo cp -a /var/lib/cns-rpi/device_binding.json \
  /var/lib/cns-rpi/device_binding.json.bak 2>/dev/null || true
git pull --ff-only
./scripts/deploy.sh
./build/cns_rpi /var/lib/cns-rpi/config.json --check-config
systemctl status cns-rpi.service --no-pager
journalctl -u cns-rpi.service -n 100 --no-pager
```

旧现场配置缺少 `mqtt.topics.runtime_status` 或 `identity.binding_file` 时，当前加载器使用固定兼容默认值；仍应在维护窗口把示例中的对应段同步到现场配置，便于审计。runtime suffix 固定为 `runtime/status/v1`、QoS 固定为 1，配置加载时会拒绝改变跨端契约的值。

回滚到 V1.0.0：

```bash
cd /home/dcdw/cns_rpi
sudo systemctl stop cns-rpi.service
git fetch --tags origin
git switch --detach v1.0.0
./scripts/deploy.sh
systemctl status cns-rpi.service --no-pager
```

回滚不删除绑定备份。若之后重新升级，恢复目标分支或提交并再次执行部署脚本。真实密码、密钥和机器专用配置不得写入仓库或验收记录。

## 6. 真机验收与原始证据

先在可访问 Broker 的运维终端持续订阅，并把原始消息保存为证据：

```bash
mosquitto_sub -h <broker地址> -p <端口> \
  -u '<用户名>' -P '<密码>' \
  -t '<namespace>/+/runtime/status/v1' -q 1 -v \
  | tee runtime-status-raw.log
```

未启用认证时省略 `-u/-P`。验收按以下顺序执行：

1. 正常启动并连接原配 F407。重新打开一个订阅者，应立即收到 retained `online | online | verified`。
2. 停止或断开 F407 业务超过 10 秒。应收到 `online | offline | <符合真实身份事实>`；同时向设备配置 Topic 发送一条合法查询或修改命令，确认 Pi 的 MQTT 控制入口仍可用。没有授权时不要实际改变现场参数。
3. 恢复原 F407。新有效业务帧与匹配 Basic ID 到达后，应回到 `online | online | verified`。
4. 在订阅者持续记录期间异常终止 Pi 进程或断开 Pi 网络。Broker 应发布 `offline | unknown | cached`；首次建绑始终失败的设备应为 `offline | unknown | unbound`。异常终止可在维护窗口使用 `sudo systemctl kill --signal=SIGKILL cns-rpi.service`，执行前确认 systemd 自动重启不会影响其他测试。
5. Pi 重新连接后，应主动发布当前 `online` retained 状态并覆盖离线遗嘱；内容按当时 F407 业务和身份事实取值。
6. Server 端同时保存 route_service 的 MQTT 接收日志、数据库该设备三态行、REST 响应和 WebSocket 原始事件；Web 页面截图只作为展示证据。五处的 `device_id` 和三态值必须一致，runtime 不得改写 registration 在线状态。

每组证据至少记录树莓派提交、配置路径、绑定文件是否存在、MQTT Topic、完整原始 JSON、Broker/Server 接收时间以及对应操作。自动化测试不能代替 Broker Last Will、F407 静默/恢复或 Server 数据库、REST、WebSocket、Web 的联合验收。
