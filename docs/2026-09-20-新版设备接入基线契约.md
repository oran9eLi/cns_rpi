# 新版设备接入基线契约

日期：2026-09-20

执行修订：2026-09-21
状态：任务 1—8 已实现并完成本地回归；云端部署与真机验收进行中。

## 1. 适用范围

本文冻结 CNS 阶段一 G0 当前有效的设备上行边界：schema v3 注册、schema v3 完整遥测快照，以及主控箱的独立运行三态。2026-09-21 合并最新 `main` 后，以下规则取代本文初版中的旧兼容假设：

- registration 与 snapshot 只接受 schema v3；schema v1/v2 和旧 `/telemetry` Topic 直接拒绝。
- 公开协议、C++ 内部模型、PostgreSQL 物理列、REST 和 WebSocket 统一使用 `device_id`；不再提供 `vendor_id` 别名。
- `device_type` 支持 `cns_box` 与 `flight_controller`。被废除的是 2026-07-27 那份旧 PX4 设备模型设计，不是最新主线已经实现的 schema v3 通用设备模型。
- `device_id` 长度为 1～20 个 ASCII 字符，只允许字母、数字、点、下划线、冒号和连字符，并必须与 MQTT Topic 中的设备段完全一致。
- 运行三态的设备侧交付对象仍是 CNS 主控箱；真实飞控没有 F407 业务链时可以保留数据库安全默认值，不要求伪造三态。

## 2. Topic 与交付语义

以下 `{namespace}` 由部署配置给出，当前默认值为 `cns_rpi`。

| 消息 | Topic | QoS | Retain | route_service 行为 |
|---|---|---:|---|---|
| schema v3 注册 | `{namespace}/{device_id}/registration` | 2 | true | 常驻订阅；维护设备类型、稳定元数据和在线状态 |
| schema v3 完整快照 | `{namespace}/{device_id}/telemetry/snapshot/v1` | 0 | false | 常驻订阅；保存每台设备最新完整快照 |
| schema v1 高频实时遥测 | `{namespace}/{device_id}/telemetry/realtime/v1` | 0 | false | route_service 不订阅、不解析、不写 PostgreSQL；由 backend_service 按页面兴趣精确订阅 |
| schema v1 运行三态 | `{namespace}/{device_id}/runtime/status/v1` | 1 | true | 常驻订阅；独立维护 Pi 控制、F407 业务和身份核验三态 |

Broker 的 retained 注册用于订阅恢复后重放设备声明的 online/offline 状态；retained 运行三态用于恢复最近一次链路事实。完整快照和实时遥测不得 retained，避免旧采样冒充新数据。

Server 冷启动时，retained registration 与 runtime 可能以任意先后顺序到达，并与新设备异步建档形成竞争。route_service 对先到达的合法 runtime 使用不超过 MQTT 输入队列容量的预注册缓存；registration 出现后，只在该设备待建档状态内保留最后一条运行三态和最后一帧完整快照，建档完成后交回原处理链，不形成历史队列。缓存达到上限后不再接纳新的未知设备；没有后续 registration 的完整快照仍直接忽略，避免任意 Topic 持续占用内存。

## 3. schema v3 注册

### 3.1 online

主控箱 online 示例见 `tests/fixtures/device/v3_registration_online.json`。

必填字段：

- `schema_version`：整数，固定为 `3`。
- `device_id`：合法统一设备标识，必须与 Topic 一致。
- `device_type`：`cns_box` 或 `flight_controller`。
- `status`：`online`。
- `school_name`：`cns_box` 必须提供非空学校；`flight_controller` 可暂未绑定学校。

可选字段：

- `dcdw_label`：非空字符串；缺失时保留数据库旧值。
- `capabilities`：非空字符串数组。
- `product`、`version`：JSON object。

online 注册可幂等重复发布。缺失可选元数据不得清空已保存值，注册中的设备类型不得与已建档设备类型冲突。

### 3.2 offline

示例见 `tests/fixtures/device/v3_registration_offline.json`。offline 只要求 `schema_version`、`device_id`、`device_type` 和 `status=offline`；省略学校、角色、能力、产品或版本时，Server 仅改变既有在线状态，不清空稳定元数据。

以下情况必须拒绝且不得修改设备：schema 不是 3；携带已删除的 `vendor_id`、`identity`、`remote_id`、`uid`、`uid2`、`gateway_id`、`rpi_serial` 或 `endpoint`；Topic 身份不一致；设备类型或状态无效；主控箱 online 缺少学校。

## 4. schema v3 完整遥测快照

示例见 `tests/fixtures/device/v3_telemetry_snapshot.json`。

协议外壳必填字段：

- `schema_version=3`；
- 与 Topic 一致的 `device_id`；
- `device_type=cns_box|flight_controller`；
- 非空字符串 `sent_at`；
- JSON object `telemetry`；
- JSON object `drone_id`，且其 `basic_id` 必须为 object。

设备唯一身份只在顶层 `device_id` 出现，`drone_id.basic_id` 不得重复携带 `uas_id`。route_service 校验外壳后保留完整 JSON；不把 `sent_at` 当作数据库权威时间，也不从快照反向覆盖注册元数据。

`telemetry_received_at` 使用 route_service 收到 MQTT 消息的服务器时间。每台设备只维护一份最新完整快照，本里程碑不保存逐帧遥测历史。

`/telemetry/realtime/v1` 是面向页面按需订阅的高频子集。route_service 不得使用通配符常驻订阅，也不得将其写入 `latest_telemetry` 或 PostgreSQL。

## 5. 主控箱运行三态

示例见 `tests/fixtures/device/runtime_verified.json` 和 `runtime_lwt_offline.json`。

全部字段均必填：

- `schema_version=1`；
- 与 Topic 一致的 `device_id`，不得同时出现 `vendor_id`；
- `control_status=online|offline`：只表示 Pi 的 MQTT 控制链可达性；
- `business_status=online|offline|unknown`：只表示 F407 最近是否有有效业务帧；
- `identity_status=verified|cached|conflict|unbound`：只表示 F407 身份核验状态。

三态不得改写 registration 的 `status`、`last_seen_at` 或遥测接收时间。Server 以消息接收时间写入 `runtime_received_at`。

### 5.1 合法组合

- `control_status=online` 时，业务和身份按真实状态取值。
- `control_status=offline` 时，`business_status` 必须为 `unknown`，`identity_status` 只能为 `cached` 或 `unbound`。
- `offline + online`、`offline + verified`、`offline + conflict` 均为非法组合，Server 必须拒绝且不改动旧状态。
- 尚无持久化合法身份时使用 `unbound`；有旧身份但本会话尚未复核时使用 `cached`；新鲜身份一致时使用 `verified`；身份不一致时使用 `conflict`，不得自动改绑。

### 5.2 发布时机与 Last Will

Pi 在三态任一字段发生变化时发布 retained 消息，不增加固定周期心跳。F407 连续 10 秒没有有效业务帧时，在 Pi 控制仍在线的前提下发布 `business_status=offline`；收到新有效业务帧后恢复为 `online`。

MQTT Last Will 表达 Pi 控制离线：

```json
{
  "schema_version": 1,
  "device_id": "DCDWCNS1S2MEAG1VTA0C",
  "control_status": "offline",
  "business_status": "unknown",
  "identity_status": "cached"
}
```

如果从未持久化合法身份，`identity_status` 使用 `unbound`。Pi 断线后 Server 无法判断 F407 的真实状态，因此 Last Will 不得把业务状态写成 `offline`。

## 6. 持久化与对外一致性

- registration 和运行三态均使用 Server 接收时间；设备时间只作为原始载荷内容保存。
- 完整快照按现有批量合并策略覆盖写入；运行三态变化立即写入，持久化成功后才发布对应状态事件。
- 运行三态由迁移 `008_增加设备运行三态.sql` 加入 `device_latest_states`；迁移 005—007 属于最新主线设备模型与 schema v3 升级，不得复用版本号。
- 旧行安全默认值为 `control_status=offline`、`business_status=unknown`、`identity_status=unbound`、`runtime_received_at=null`。
- retained 设备目录、单设备状态、backend_service REST/WebSocket 和 Web 使用同名 `device_id` 与三态字段。
- route_service、backend_service 和 Web 对枚举的理解必须一致；未知枚举在边界拒绝，不能静默映射为正常状态。

## 7. 验收边界

G0 至少验证：

- schema v3 主控箱与真实飞控注册/快照回归通过，schema v1/v2 被拒绝；
- 完整快照原样进入最新状态，高频 realtime 不被 route_service 订阅或持久化；
- 运行三态不覆盖 registration `status`；
- F407 静默 10 秒只改变业务状态；
- Pi 异常断线由 retained Last Will 形成 `offline|unknown|cached` 或 `offline|unknown|unbound`；
- 恢复后使用新鲜事实回到 `online|online|verified`；
- route_service、backend_service、Web 与 PostgreSQL 对 `device_id` 和三态字段一致。

本文不定义 Experiment、Session、实验动作、设备租约、评分或导出；这些能力由后续里程碑另行设计和确认。
