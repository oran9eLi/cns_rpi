## 现场配置与旧卷退出

虽然当前本地方案已取消只读卷，部署前这台 Pi 的 `/var/lib/cns-rpi` 仍是旧 ext4 loop 只读挂载，且 `cns-rpi-config.service` 仍启用。本次按普通可写目录方案处理：

1. 备份原程序、现场配置、源码、服务单元、配置辅助程序、完整配置卷内容及其底层目录内容，并备份启动配置和旧卷镜像。
2. 停止主服务，停用旧配置服务，通过其正常停止流程卸载旧卷；确认卸载完成后，将原卷内容还原到普通目录。
3. 用原子配置写入辅助程序应用新配置；以同目录临时文件和重命名替换主程序。
4. 移除旧配置挂载单元及其启用链接，并移除主服务对它的 `Requires/After` 依赖，重新加载 systemd，启用并启动主服务。

`/var/lib/cns-rpi` 现位于根文件系统 `/dev/mmcblk0p2` 的普通 ext4 可写目录，归属 `dcdw:dcdw`、权限 0755；`config.json` 归属相同、权限 0600。旧挂载单元和启用链接不存在，主服务不再依赖它。原 `/boot/firmware/cns-config.img` 保留但不再挂载，独立核对其哈希与备份一致。本次未重启 Pi，未做断电恢复验证。

实际配置变更：

```json
{
  "video": {
    "enabled": true,
    "executable": "/usr/bin/rpicam-vid",
    "ffprobe": "/usr/bin/ffprobe",
    "work_directory": "/tmp/cns-rpi-video"

```

同时显式写入原默认值 `identity.binding_file=/var/lib/cns-rpi/device_binding.json` 和 `mqtt.topics.runtime_status={"suffix":"runtime/status/v1","qos":1}`。新程序配置校验和现有 5G 程序配置加载均通过。与安装前备份逐项比较，`serial`、`cellular`、`mqtt.connection`、`mqtt.auth` 完全一致，未改动 MQTT 凭据。未改动或重启 5G 服务。

启用视频只开放操作入口，不会自动开始持续采集。测试结束后没有留下摄像或收流进程。

## ARM64 构建与专项验证

在 Pi 使用 GCC 14.2、CMake 3.31.6、Ninja 原生编译。考虑目标机内存，Release 优化设为 `-O1 -DNDEBUG`，并行度为 2。

```sh
cd /home/dcdw/cns-rpi-deploy/g2-20261105
cmake -S source -B build -G Ninja \
  -DCMAKE_BUILD_TYPE=Release '-DCMAKE_CXX_FLAGS_RELEASE=-O1 -DNDEBUG'
cmake --build build -j2 --target \
  cns_rpi test_video_manager test_video_request test_video_experiment test_app_config \
  test_device_binding_store test_device_session test_systemd_watchdog test_mqtt_client
ctest --test-dir build --output-on-failure \
  -R '^(video_manager|video_request|video_experiment|app_config|device_binding_store|device_session|systemd_watchdog|mqtt_client|release_cli)$'
```

结果为 **9/9 通过，4.04 秒**；这里不是全量 57 项 ARM64 测试，也未启用测试内可选的真实 Broker 收发/重连用例。此前 WSL 的全量 57/57 和真实 Broker 结果单独记录于 [接口与本地验证](G2树莓派视频实验接口与本地验证.md)。

原生构建成功，但有 5 条既有时间戳格式的 `-Wformat-truncation` 告警，位置分别为 `pi_link_inspection.cpp:100`、`link_lab.cpp:107`、`deferred_serial_request.cpp:24`、`m1_transaction.cpp:59`、`uart_echo_transaction.cpp:45`，均不属于本轮视频新增源码；本次未扩大范围修改它们。不能将该原生构建称为零告警。完整输出保存在暂存目录 `build.log`。

## 实拍与 SRT 证据

维护测试程序 `video-smoke` 直接编译并调用与主程序相同源码的 `video::Manager`，使用固定维护参数，不伪造 F407 身份，也不经过生产 MQTT 控制链。

| 验证 | 实测结果 |
|---|---|
| 摄像头枚举 | 完成，camera 0 为 `imx708_wide` |
| 有限采集 | 请求 3 秒、1280×720、25 fps、2 Mbps；ffprobe 确认 H.264、实际 1280×720、65 编码帧、编码时长 2.5991 秒 |
| SRT 发送 | 新 Manager 推送到 `srt://127.0.0.1:18900?streamid=publish:g2/readiness&pkt_size=1316`，请求时长 3 秒 |
| SRT 接收 | Pi 本机 ffmpeg SRT listener 接收，生成 TS 704060 字节；ffprobe 确认 H.264 Constrained Baseline、1280×720、无 B 帧、66 帧、时长 2.639089 秒 |
| 停止与清理 | 测试任务完成，无忙状态；子进程均回收，有限采集临时文件由 Manager 清理 |

3 秒是请求的采集时长，编码时长按实际 ffprobe 结果记录。2 Mbps 是请求参数，不是网络实测吞吐量。CSI 到 SRT 接收只在同一台 Pi 内完成；不代表远端接收、MediaMTX、浏览器解码或网络延迟通过。

取证文件位于暂存目录：`camera-probe.json`、`camera-test.json`、`srt-sender.json`、`srt-summary.json`、`srt-receiver.log` 和 `srt-received.ts`。辅助程序和执行脚本亦保留于该目录，未加入产品启动流程。
